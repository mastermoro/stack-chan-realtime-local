# Face の再生停止: 切り分けと受け入れ確認 (#12)

対象: [issue #12](https://github.com/mastermoro/stack-chan-realtime-local/issues/12)。
基準コミット: `1dd9257291a0f4fe7c8aa38cc8050533ea949116`。

## ソフトウェア上で確認できる問題

- Face の割り込みは再生を止めて即座に `LISTENING` へ戻るが、会話を継続するため
  `conversation_active` は true のまま。既に転送中の古い `speaking` が状態を戻すと、
  その後の PCM が再び再生される。単純に会話を false にすると即時の聞き取りを壊す。
- USB ブリッジは一つの PCM を20ms単位に分割・ペーシングしている。割り込みを Relay
  へ転送するだけでは、ペーシング中の残りや WebSocket に滞留した古い PCM は消えない。
- Relay の抑制チェックと実際の送信の間には await があり、チェック後に割り込みが
  入ると古い出力処理が再開する。キャンセル済みの `response.done` が新しい listening
  を ready に上書きする経路もある。
- USB 受信の `while (Serial.available())` は入力が続くと UI へ制御を戻さない。
  同期的なスピーカー処理と重なるため、タッチ受付遅延の別の要因になる。

これらはコードと決定的な回帰テストで確認する競合条件であり、報告された実機での
唯一の原因を特定したという意味ではない。実機のタッチ遅延、スピーカー停止時間、
Windows USB ドライバー、Foundry との実通信は別途確認が必要。

## 修正方針

最新の interrupt_id と一致する Relay の確認を、順序付き出力ストリームの境界として
使う。端末はローカル停止後、その境界まで古い出力を受け付けない。USB ブリッジは
ペーシングを中断して境界まで素早く読み捨てる。Relay は境界後に古い送信が残らない
よう直列化する。キャンセル完了が遅れても新しい聞き取り状態を上書きしない。
USB 受信処理には上限を設け、継続入力でもタッチ処理に戻る。

Foundry のキャンセルエラーは client event_id が省略される場合がある。割り込み処理中に
ID のない「no active response」エラーが届いた場合、古いキャンセルの返答かどうかを
判別できないため、Relay は既存の再接続経路で Foundry セッションを作り直す。
この復旧やキャンセル送信失敗・フェンス喪失からの接続復旧では、会話コンテキストが
リセットされる。単に抑制を解除したり、無期限に
ミュートしたりしない。通常の ID 付き確認では同じセッションを維持する。
[Microsoft の Realtime API リファレンス](https://learn.microsoft.com/en-us/azure/foundry-classic/openai/realtime-audio-reference-ga#responsecancel)
と SDK の任意 event_id 定義に合わせた安全な復旧策である。

詳細と更新順序は [protocol.md](protocol.md#再生割り込みのフェンスissue-12) を参照。
音声内容、認証情報、文字起こしは追加の診断ログへ記録しない。

## 実機チェック（未実施）

Relay と USB ブリッジを更新・再起動した後、同じ変更のファームウェアを書き込む。
USB と WI-FI の各固定モードで以下を行う。AUTO でも会話後の切り替えを確認する。

1. Face から会話し、10秒以上の長めの応答を依頼する。
2. 再生の始め・途中・終わりで、左上のカメラ領域を避けて顔をタップする。
   タップ直後に音が止まり、古い声が再開せず `LISTENING` に戻ることを確認する。
3. タップ直後に次の質問を話し、新しい応答が聞けることを確認する。各条件を5回以上
   繰り返し、次の応答も再度割り込めることを確認する。
4. 連続タップで聞き取りの一時停止・再開を試す。古い確認や完了通知で状態が巻き戻らず、
   最後の操作に従うことを確認する。
5. THINKING / SEARCHING 中の割り込み、Status の一時停止、上面ダブルタップの睡眠も確認する。
6. USB の長い再生中にタッチが認識されるか観察する。可能なら別端末で画面と音を同時に
   記録し、タッチ→無音とタッチ→LISTENING の遅延を修正前後で測る。
7. USB 抜き差し、Relay 再起動、Foundry 再接続後に会話・割り込み・次の応答を確認する。

ブリッジログの `USB output interrupted id=...` と `USB output fence queued id=...`
が対応するか確認する。ID は操作の識別子であり音声内容ではない。
停止しない場合は接続モード、タップ場所、画面状態、各ログの時刻、ビルドのコミットを
記録する。確認が届かない場合は Relay / ブリッジ / ファームウェアの更新ずれを先に確認する。

## 再検証で追加した復旧と設計上の選択

- SDK の `response.cancel` 送信失敗は、API の「応答なし」エラーとは異なる。
  配信が不明な旧接続の抑制を維持したまま上流を作り直す。遅れて到着する旧 created /
  done / error が抑制を解除する経路も塞ぐ。
- 切断処理がフェンス送信中のタスクをキャンセルする場合も、フェンス処理を回収して
  から上流を置き換える。終了済み接続の送信タスクを残さない。
- USB ホストも送信キューが空になるまで無制限に排出せず、最大4フレームごとに端末の
  入力を読む。継続送信で pause の受信が飢餓状態になるケースを実 worker ループで再現した。
- フェンス等の制御フレームを USB 送信キューに入れられない場合は、確認済みとして扱わず
  Relay 接続を閉じる。送信後に CRC エラー等で失われた場合も、端末の確認期限で検出する。
- 確認が5秒届かない場合は旧トランスポートを切断する。時間だけで再生を許可しない。
  USB 復旧は DeviceOpen の recovery_id を新規接続後の HostOpenAck に返すことで、
  滞留した旧 OpenAck が出力を再開することを防ぐ。

順序付きストリームのフェンスを使い、PCM 自体の形式や USB エンベロープの版は変更しない。
全 PCM に世代ヘッダーを付ける方法より変更範囲を限定し、旧クライアントを維持する。
一方、フェンス喪失や上流キャンセル失敗時は、旧履歴の継続より安全な再接続を優先する。

RelaySession とペーシング中の UsbBridge を直接つなぐ統合テストも追加し、単一・連続
割り込みで古い音声が出ず、最新フェンスより後に次ターンの音声が出ることを確認する。

USB の2ms上限はループの協調的な処理予算であり、実行中の playRaw / JSON 処理を
プリエンプトするものではない。従ってタッチ→無音の実時間上限は主張しない。
実機の受け入れ条件は、上記チェックリストに沿った計測を残す。


追加改善の検証結果:

- キャンセル送信失敗の旧 PCM 漏れ、フェンス送信中のキャンセル、USB ホストの継続送信による
  受信飢餓、フェンス投入失敗、失われた確認の期限復旧は修正前に失敗を確認した。
- 再接続前の USB バッファに HostClose → 空 HostOpenAck → Speaking → PCM を入れてから
  タップする境界も、対応する recovery_id の新規ハンドシェイクまで遮断される。
- ローカルの実 FastAPI / Uvicorn / WebSocket / TCP で読み取り停止による送信バックプレッシャーを
  作り、クライアント切断で送信とキャンセル保護中のフェンスが終了することを確認した。
  切断にも反応しない人工的な無期限 send は残る制約であり、終了処理の厳密な時間上限は保証しない。
- 通常の Face 割り込み成功時は直ちにマイクを再開する。確認喪失等でトランスポートまで
  作り直した場合は、Status の詳細に CONVERSATION RESET を設定し、次のタップから
  新しい会話を始める。通常の Face は詳細オーバーレイを隠しているため、Face 上で
  常にリセット通知が見えることは保証しない。
